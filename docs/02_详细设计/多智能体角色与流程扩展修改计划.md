## 1. 背景

### 1.1 现状

Daedalus 当前是一支 **面向 SWE-bench 缺陷修复场景的单一流水线团队**：

| 层级          | 现有实体                                                                     | 说明                                        |
| ----------- | ------------------------------------------------------------------------ | ----------------------------------------- |
| Manager     | `default-manager.yaml`                                                   | 接收外部任务、创建协作房间（薄壳角色）                       |
| Team Leader | `coordinator`（`rd-defect-team.yaml` 中 `spec.leader`，role: `team_leader`） | 派单、等待回包、超时重发、输出最终 `Verdict: SUCCESS/FAIL` |
| Worker × 4  | `analyzer` / `fixer` / `tester` / `evaluator`                            | 根因分析 → 代码修复 → 测试执行 → 质量评审                 |

场景上仅支持 bug fix：admin 消息以 `New SWE-bench task` 开头即触发固定线性流水线  
`analyze → fix → test → evaluate`。

### 1.2 扩展诉求

将组织形态贴近真实软件公司，并支持更丰富的场景：

1. **角色重塑**：analyzer → Architect（架构设计与技术选型）、fixer → Developer（广义开发）、tester 不变、evaluator → 评审并对最终质量负责的角色、**新增 PO**（需求分析与产品设计）；
2. **场景扩展**：bug fix 沿用现有流程；new feature 走 `PO → Architect → Developer → Tester → 评审`，任一环节发现问题回退至相应角色直至超出重试限制；0→1 新项目视为特殊 new feature；
3. **运维接入**：新增 incident 任务类型（出了问题但不确定是否代码问题），由运维角色先诊断生产环境——环境异常则按 runbook 处置（高危操作仅出建议、人执行），非运维问题则转 bug 流程；运维与开发形成「动态环境问题 vs 静态代码问题」的分工。

### 1.3 源码层面的关键现状（本次设计的约束输入）

评审现有代码发现以下事实，直接决定修改方案的形态：

## 2. 修改目标

### 2.1 目标

| #  | 目标                                                                                          | 度量                                             |
| -- | ------------------------------------------------------------------------------------------- | ---------------------------------------------- |
| G1 | 角色体系对齐真实软件公司：Team Leader / PO / Architect / Developer / Tester / Reviewer / Ops Analyst 七角色 | 角色职责表落地，技能分配无重叠、无空洞                            |
| G2 | 支持 incident / bug / feature（含 greenfield 特例）三类任务信封，按类型自动路由                                  | 三类任务各有一条可运行的状态机路径（feature 含 greenfield 变体）     |
| G3 | 回退机制从"纸面设计"变为运行时事实：回退有仲裁、有粒度、有双闸门                                                           | coordinator soul 含回退分支；pipeline-router 实际挂载并执行 |
| G4 | bug fix 场景 **零劣化**：SWE-bench Verified 通过率不低于改造前基线                                           | 回归验证（改造前先跑基线）                                  |
| G5 | 阶段间工件契约化：PRD / ADD / 诊断报告 有 JSON Schema，下游可机读消费                                             | schema 文件随技能包交付                                |
| G6 | 运维接入：incident 可完成"环境诊断 → 分流（处置建议 / 转 bug）"闭环，生产环境**零直接变更**（L1/L2 全部人执行）                     | incident 端到端验收 + 生产变更审计记录为空                    |
| G7 | 前端视觉可判定：feature / greenfield 的前端任务可自动核验视觉质量（对齐/间距/对比度/溢出等），不依赖人工看图（§3.12） | 前端任务端到端：ADD 含 `ui_spec`、Developer 自检、Tester 视觉回归、Reviewer 核验；视觉违规可触发 `failure_class=visual` 回退 |

### 2.2 非目标（本次不做）

- 不引入 CI/CD 灰度发布角色（release_plan / release_decision 脚本保留，接线后置）；
- 不做多任务并发调度与 backlog 排序（PO 单任务串行）；
- 不改动 `mcp_server` 的 MCP 原语层接口（仅改角色字符串与重复的状态机定义）；
- 不做旧 Matrix 房间历史迁移（改名即新部署，接受历史断裂）；
- **不追求"有创意/品牌级"的视觉设计**（§3.12.7）：前端视觉目标锁定"专业、一致、可用"，不引入多模态视觉判断（通道 B 仅预留接口），设计师级诉求经 Gate0 标记后 `escalated` 转人工；
- **不为 bug 场景引入视觉流程**（§3.12.2 执行约定 4）：`visual_check` 仅服务 feature / greenfield，避免给高频 bug 流增加成本与延迟。

## 3. 设计决策

### 3.1 角色定稿

> 决策 D1：**coordinator 升格为 Team Leader**（保留平台 `spec.leader` 语义与 runner 依赖的派单/Verdict 协议），**evaluator 更名为 Reviewer** 而非 Team Leader——规避双 leader 冲突（F1）。

| 角色                  | 实体来源                   | 定位               | 关键职责                                                                                                                                                                | 模型建议                         |
| ------------------- | ---------------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **Team Leader**     | 现 `coordinator`        | 平台 leader、流程所有者  | ① 任务信封解析与场景路由；② 派单与超时重发；③ **回退仲裁**（裁决 failure_class → 回退目标）；④ 重试双闸门计数；⑤ 最终 Verdict；⑥ escalation                                                                     | DeepSeek-V4-Pro（SiliconFlow，见 §3.10） |
| **PO**（新增）          | 新 worker `po`          | 需求侧              | ① 需求分析 → PRD（接管现 analyzer 流程 B，见决策 D2）；② **需求歧义澄清（Gate0，见 §3.11）：以 DoR 检查表卡住歧义，经 User Channel 阻塞等待用户澄清，禁止自造需求或默认假设**；③ greenfield 场景定义 MVP 边界；④ 扩展交付物（用户故事 / 需求清单 / 术语表 / 需求追踪矩阵，见 §3.6.1，均以 PRD 为唯一契约）                                                                              | Qwen3.6-35B-A3B（SiliconFlow，见 §3.10）                   |
| **Architect**       | 现 `analyzer`           | 分析侧，**双流程**      | 流程 A（bug）：根因分析——语义锚定 / KG 调用链 / 复现脚本，**完全沿用现有 analyzer 流程**；流程 B（feature）：架构设计——优先读 repo `docs/` 既有设计文档，无文档则从源码逆向，产出 ADD（扩展交付物见 §3.6.2，均以 ADD 为唯一契约）                                            | kimi2.7code（SiliconFlow，见 §3.10）                 |
| **Developer**       | 现 `fixer`              | 开发侧              | bug：最小修复；feature：按 PRD+ADD 实现（输入集含 PRD+ADD+Charter 作辅助上下文，见 §3.9.3）；greenfield：脚手架搭建                                                                                                                      | DeepSeek-V4-Pro（SiliconFlow，见 §3.10）                   |
| **Tester**          | 不变                     | 质量证据             | bug：复现/针对性/回归三段式；feature：**从 PRD 验收标准独立设计用例（先于开发完成），再执行**；greenfield：按 PRD 全量用例                                                                                     | DeepSeek-V4-Pro（SiliconFlow，见 §3.10）                          |
| **Reviewer**        | 现 `evaluator`          | 质量门禁             | code review（保留 KG 影响面分析）；对照 PRD 独立验收；驳回时附 `failure_class` 分类建议；经验沉淀（knowledge-extraction）；**参与 feature 双共识闸门**（§3.8：PRD 评审 gate + 设计评审 gate 的共识方与 sign-off 持有者）；终检作为 Team Leader 给出 `SUCCESS` Verdict 的前置条件           | **GLM-5.2**（SiliconFlow 审查最强，见 §3.9 + §3.10）                          |
| **Ops Analyst**（新增） | 新 worker `ops-analyst` | 生产环境侧，**只诊断不执行** | ① incident 分诊：环境健康检查（服务状态/端口/进程/磁盘/网络/配置漂移）；② 依据 runbook + 部署文档 + 历史事件诊断；③ 产出诊断报告 + L0/L1/L2 分级处置建议（L1/L2 由人执行）；④ 诊断为代码问题 → 归一化为 bug 流程并携带证据包；⑤ 事后沉淀 runbook/lesson | DeepSeek-V4-Pro（SiliconFlow，见 §3.10）；需接入生产只读通道              |

> 七角色均须遵循 §3.7 Engineering Charter（共享价值观 + 角色专属方法论），Charter 作为跨角色约束的单一来源，避免各角色 soul / SKILL.md 各自硬编码原则导致不一致。

> 决策 D2：analyzer 的「流程 B：需求规格化」**整体迁移给 PO**，其 feature_request JSON 扩展为 PRD schema（§3.5）；Architect 的 soul 中删除流程 B，避免双头产出（F2）。
>
> 决策 D3：**Architect 保留双流程**（根因分析 + 架构设计）。理由：bug fix 场景"沿用现有流程不变"的前提是仍有角色做根因分析；"及相关分析工作"在职责表述中显式涵盖根因分析，而非只留架构设计。
>
> 决策 D4：**Reviewer 保留 evaluator 的 KG 影响面审查**（neo4j_impact_stats / dep_subgraph），这是现有质量门禁的核心资产，不因更名弱化。

### 3.2 场景流水线与状态机

> 决策 D5：引入**结构化任务信封**，替代 `New SWE-bench task` 单一触发词（F5）。

**任务信封（admin → Team Leader 的消息协议）：**

```json
{
  "task_type": "incident | bug | feature",
  "task_id": "INC-XXXX | SWE-XXXX | FEAT-XXXX",
  "repo": "MinIO 对象键；feature 场景为空即判定为 greenfield",
  "env": "目标环境标识（incident 必填，如 prod）",
  "base_commit": "可选，bug 场景必填",
  "requirement": "描述原文（incident=症状描述 / bug=错误行为 / feature=需求）",
  "priority": "P0-P3"
}
```

> 决策 D8：任务类型收敛为 **incident / bug / feature 三类**；greenfield 不再是独立类型，而由 `repo` 为空自动判定为 feature 的 greenfield 变体（与"从 0 到 1 视为特殊 new feature"的原始诉求一致）。

兼容性：以 `New SWE-bench task` 开头的旧格式消息由 Team Leader 归一化为 `task_type=bug`，保证 `swe_bench_runner.py` 平滑过渡（阶段 4 才改 runner，此前完全兼容）。人工提交的**未分类**问题报告默认按 `incident` 入口进入分诊。

**场景流水线（状态机）：**

```mermaid
stateDiagram-v2
    [*] --> received: 任务信封
    received --> triaging: Team Leader 解析/路由

    state "incident 流水线（新增）" as inc {
        ops_diagnosing --> ops_remediation
    }
    triaging --> ops_diagnosing: task_type=incident
    ops_remediation --> resolved: 环境问题·人执行处置后确认
    ops_diagnosing --> analyzing: 诊断为代码问题·归一化为 bug（携带诊断报告）

    state "bug 流水线（沿用现状）" as bug {
        analyzing --> fixing --> testing --> evaluating
    }
    triaging --> analyzing: task_type=bug

    state "feature 流水线（新增）" as feat {
        clarifying
        clarifying --> prd_drafting: DoR 满足(§3.11)
        clarifying --> clarifying: 等待用户澄清
        prd_drafting --> prd_review
        prd_review --> designing: 共识通过(Reviewer sign-off)
        prd_review --> prd_drafting: 驳回·返回修改
        designing --> design_review
        design_review --> developing: 共识通过(Reviewer sign-off)
        design_review --> designing: 驳回·返回修改
        developing --> test_designing --> test_executing
    }
    triaging --> clarifying: task_type=feature

    state "greenfield（feature 特例，repo 为空）" as gf {
        clarifying_g
        clarifying_g --> prd_drafting_g: DoR 满足(§3.11)
        clarifying_g --> clarifying_g: 等待用户澄清
        prd_drafting_g --> prd_review_g
        prd_review_g --> designing_g: 共识通过
        prd_review_g --> prd_drafting_g: 驳回
        designing_g --> design_review_g
        design_review_g --> bootstrapping: 共识通过
        design_review_g --> designing_g: 驳回
        bootstrapping --> developing_g --> test_executing_g
    }
    triaging --> clarifying_g: task_type=feature 且 repo 为空

    analyzing --> ops_diagnosing: 复现失败·failure_class=environment（回流复查）
    evaluating --> awaiting_release
    test_executing --> awaiting_release
    test_executing_g --> awaiting_release
    awaiting_release --> resolved
    awaiting_release --> escalated
```

要点：

- **feature 场景测试设计前置**（`test_designing` 与 `developing` 可并行，Tester 从 PRD 验收标准派生用例，不依赖实现，规避自我验证陷阱）；
- **feature 需求澄清闸门（Gate0，详见 §3.11）**：`triaging` 之后、`prd_drafting` 之前插入 `clarifying` 状态；PO 以 DoR 检查表卡住歧义需求，经 User Channel 阻塞等待用户澄清（Jira comment 置 Needs Clarification / 聊天室对话），**禁止自造需求或默认假设**；仅 feature / greenfield 开启，bug / incident 不开启，避免在无澄清下直接进 PRD。
- **feature 双共识闸门**（详见 §3.8）：`prd_review`（PO + Architect + Reviewer 对 PRD 可行性/完整性共识）位于 PRD→设计前，`design_review`（Architect + Developer + Reviewer 对设计可实施性共识）位于设计→开发前；两处闸门的共识参与者均为 **Reviewer**（独立质量门禁），Team Leader 仅作流程所有者与终裁，不参与闸门讨论本身。闸门驳回回路复用 D6 分类回退协议。
- **greenfield 特殊化**（对应 F5）：
  - 跳过 MinIO 拉仓库与 repo-index 索引；
  - Developer 增加 `bootstrapping` 脚手架步骤（语言/框架模板由 ADD 指定）；
  - **前端脚手架预装设计系统**（§3.12）：模板内置成熟组件库与设计令牌（推荐 React + Ant Design），使 `ui_spec.design_tokens` 从第一天就有可消费对象——greenfield 无存量页面可提取基线（§3.12.2 执行约定 2），**脚手架即基线**，这是 greenfield 前端视觉下限的唯一保障；
  - 无回归测试套件，验收完全以 PRD 为准；
  - 工作区仍遵循 `/tmp/swe/{id}/` 隔离规范。
- **incident 分诊是双向的**（详见附录 A）：
  - ops_diagnosing 的诊断报告作为**证据包**随归一化后的 bug 任务传递——Architect 做根因分析时直接继承运维已排除的变量（网络/磁盘/依赖服务/配置漂移）；
  - 反向回流边：bug 流程中 Architect 复现脚本**无法复现**时，以 `failure_class=environment` 回退 Ops Analyst 复查，避免 Developer 空转。

### 3.3 回退与重试机制

> 决策 D6：回退采用「**分类建议 → Team Leader 仲裁**」两级机制，配双闸门计数。

**failure_class 分类协议**（Reviewer / Tester 报告问题时必须附带）：

```json
{
  "failure_class": "code | design | requirement | environment | visual",
  "evidence": "失败证据（测试输出 / diff 审查结论 / PRD 条目编号 / 复现失败记录 / 视觉检查报告）",
  "suggested_rollback_target": "developer | architect | po | ops-analyst",
  "details": "具体问题描述，含行号/PRD 条目引用/环境检查项"
}
```



| failure_class | 典型症状                      | 回退目标                                |
| ------------- | ------------------------- | ----------------------------------- |
| `code`        | 用例失败、实现与 ADD 契约不符         | Developer（局部重做，保留其旧产物版本）            |
| `design`      | 模块划分/接口契约缺陷、影响面失控         | Architect（ADD 修订；Developer 产物标记待评估） |
| `requirement` | PRD 歧义、验收标准本身矛盾           | PO（PRD 修订；触发下游全链失效告警）               |
| `environment` | 复现脚本无法复现、症状间歇出现、疑似环境/配置漂移 | Ops Analyst（环境复查；Developer 产物保留待评估） |
| `visual`      | 视觉回归失败（对齐/间距/对比度/溢出等违反 ui_spec 或 PRD 视觉验收标准） | Developer（局部重做；Developer 自检循环超限后才上报，见 §3.12.3） |

**双闸门计数（对齐 pipeline-router 现有阈值体系）：**

| 闸门     | 阈值                  | 超限动作                                            |
| ------ | ------------------- | ----------------------------------------------- |
| 单阶段重试  | 每阶段 ≤ 2 次           | 阶段升级：向更早阶段回退一级（如 Developer 两次失败 → 回退 Architect） |
| 全局轮次   | `MAX_ROUND = 3`（沿用） | `escalated` 转人工，生成 handoff 包（沿用 `handoff.py`）   |
| 回退至 PO | 全局仅 1 次             | 需求级返工代价高，第二次直接 escalated                        |

仲裁规则：Team Leader 收到带 `failure_class` 的驳回后，有权改判分类（如 Tester 报 code 但证据显示契约缺失则改判 design）；回退时在消息中显式携带 `round_num` 与目标阶段，供状态机校验。

### 3.4 阶段间工件契约

> 决策 D7：PRD / ADD 均为 JSON 工件，经 MinIO（`prd.json` / `add.json`）传递，schema 随技能包交付。

> 说明：PRD / ADD JSON 是 Agent 间消费的**唯一机读契约**（G5）；"用户故事 / 验收标准 / 接口规范 / 技术选型 / 风险清单"等扩展视图由 §3.6 规定，可经"增量融合"沉淀进主设计文档，但**不替代** MinIO 上的 `prd.json` / `add.json`。

**PRD schema（PO 产出，由现 feature_request JSON 扩展）：**

```json
{
  "task_id": "FEAT-XXXX",
  "task_type": "feature",
  "intent": "一句话本质意图",
  "functional_requirements": ["..."],
  "non_functional_requirements": ["性能/兼容性/安全约束"],
  "ambiguities": [{"point": "...", "interpretations": ["..."]}],
  "acceptance_criteria": [{"id": "AC-1", "given": "...", "when": "...", "then": "..."}],
  "visual_acceptance": [{"id": "VA-1", "check": "页面无横向溢出，空态有引导文案；表格行高一致，操作按钮右对齐（可宽松，用于视觉回归与 Reviewer 核验）"}],
  "boundary_conditions": {"must_cover": ["..."], "can_skip": ["..."]},
  "out_of_scope": ["显式排除项"],
  "greenfield": {"mvp": ["MVP 范围"], "tech_constraints": ["语言/框架约束（greenfield 必填）"]}
}
```

> `visual_acceptance` 为 v1.8 新增字段（决策 D23，详见 §3.12）：feature / greenfield 前端相关任务必填；以可核验的视觉 Given-When-Then 描述（对齐/间距/状态呈现等），供 Tester 派生视觉回归用例、Reviewer 逐项核验。纯后端任务可省略。

**ADD schema（Architect 产出）：**

```json
{
  "task_id": "FEAT-XXXX",
  "design_inputs": {"docs_referenced": ["docs/xxx.md"], "code_analyzed": ["模块/符号"], "docs_code_divergence": ["文档与代码不一致处及采信结论"]},
  "tech_stack": {"choices": [{"component": "存储", "selected": "PostgreSQL", "rationale": "..." , "alternatives_rejected": ["..."]}]},
  "design_patterns": [{"pattern": "Repository", "applied_in": "数据访问层", "solves": "解耦业务逻辑与存储，便于切换与测试替身"}],
  "dependencies_rationale": [{"name": "pydantic", "category": "mainstream", "selected": ">=2.0", "reason": "社区主流、安全维护活跃", "alternatives_considered": "marshmallow", "risk": "低"}],
  "ui_spec": {"design_tokens": {"source": "antd", "palette": ["..."]}, "component_mapping": ["页面 → 组件清单"], "interaction_states": ["每页 × empty/loading/error/boundary"], "layout": {"grid": "8pt", "breakpoints": ["..."]}, "baseline_sources": ["存量页面/参考截图路径"]},
  "module_design": [{"module": "...", "responsibility": "...", "public_interface": ["签名"]}],
  "data_model": ["..."],
  "api_contracts": ["..."],
  "change_plan": [{"file": "...", "change": "new|modify|delete", "risk": "低|中|高"}],
  "rollout_risks": ["..."]
}
```

> `ui_spec` 为 v1.8 新增字段（决策 D23，详见 §3.12）：前端相关任务必填，Architect 产出，Developer 实现契约，Reviewer 核验。`design_tokens` 要求显式引用成熟设计系统（Ant Design / Material Design 3）而非自创；`interaction_states` 覆盖 empty/loading/error/boundary 四态；`baseline_sources` 记录 Architect 用 visual_check 从存量页面提取的视觉基线。

`docs_code_divergence` 字段显式记录「文档 vs 代码」分歧及采信结论，回应 F6：Architect 优先精读 `docs/`（新增 docs-read 步骤，裸读文件即可起步，docs 索引化列为后续优化项，不阻塞本次）。

`design_patterns` 与 `dependencies_rationale` 为 §3.7 Engineering Charter 在 Architect 产出上的强制落点：`design_patterns` 要求显式命名采用的 GOF 模式及解决的问题；`dependencies_rationale` 要求对第三方依赖按 `mainstream / niche / self-built` 标注选型理由与风险（呼应 Charter "优先采用而非自研"原则）。二者缺失即视为 ADD 不完整，Reviewer 据 D17 驳回。

### 3.5 运维接入（incident 场景）

> 决策 D9：**运维按"只诊断、不执行"接入**——生产操作分 L0（只读，自动执行）/ L1（可逆低危，出建议人确认）/ L2（不可逆高危，只出报告人执行）三级；第一阶段 L0 全放开、L1/L2 全部由人执行，Agent 对生产环境**零直接变更**（G6 验收项）。诊断报告 schema 见附录 A.3。
>
> 决策 D10：**环境异质性作为"数据"而非"能力"吸收**——运维侧的标准接口是 **runbook + 环境资产包**：Agent 的能力定义在诊断流程骨架上（与 Architect「优先读 docs，无文档则逆向分析」对称：Ops Analyst 优先读 runbook，无 runbook 则按通用诊断 playbook 降级），各产品环境差异全部沉淀在随环境交付的资产包数据里（附录 A.4）。
>
> 决策 D11：**运维单角色起步**（Ops Analyst），不预建执行/值班角色。拆分触发条件：L1 级审批代执行基础设施（审批工单 + 操作审计 + 回滚点三件套）落地时，再拆 Ops Responder；告警/值班集成需求出现时，再考虑 On-call 编排。

**运维技能盘点结论**（详细分析见附录 A.5）：现有 15 个技能中 4 个可直接复用（bash-exec / code-read / lesson-lookup / knowledge-extraction），需新增 2 个（ops-diagnosis 诊断方法、env-inventory 环境资产包读取约定）；不新增 MCP 原语。

> 决策 D12：**PO 的交付物以 PRD JSON 为唯一机读契约（G5）**——"用户故事 / 验收标准 / 需求清单"等是 PRD 的视图或字段扩展，不另起独立文档；仅在 PRD schema 中按需增补字段（如 `user_stories` / `glossary` / `requirement_traceability`），或作为 §3.6.3 的融合段落并入主设计文档。

>
> 决策 D15：**Architect 的 ADD 人类可读沉淀推荐对齐 arc42 模板结构**，并将绘图统一收敛为 mermaid（首选，代码即文档、diff 友好、随主设计文档增量融合）与 drawIO（复杂图，导出 SVG/PNG 入 `asset/` 并链接）两类，避免自由格式抬高下游消费成本。

#### 3.6.3 文档增量融合策略（feature vs greenfield）

**核心规则（D14）**：主设计文档 `docs/02_详细设计/研发缺陷闭环协同系统详细设计_v3.md` 是**系统级知识主干**（角色、流水线、回退机制、既有 ADD/PRD 基线）；新功能的需求与设计以"局部更新"方式并入，而非新建功能文档。

**feature（现有项目，repo 非空）融合约定：**

1. **锚点（Anchor）**：每个功能以 `FEAT-XXXX` 为稳定锚点，新增章节命名形如：
   - 需求侧：`## N.M 功能需求：<FEAT-ID> <一句话标题>`（并入"需求与功能"章）
   - 设计侧：`## P.Q 详细设计：<FEAT-ID> <一句话标题>`（并入"详细设计"章）
2. **局部更新（Local Update）**：仅追加新章节 / 修订受影响的既有小节（如新增模块在"系统模块总览"补一行），**不重写整章、不整体覆盖**；类比 PR 的 diff，而非整文件替换（mermaid 代码随章节 diff 生效；drawIO 导出图随章节更新重导并在融合段落标注图 ID 与日期）。
3. **变更留痕（Changelog）**：章节头部以 `> 融合自 FEAT-XXXX，YYYY-MM-DD` 标注来源与日期，供 Reviewer 对照 PRD/ADD 做 delta 验收（呼应 Reviewer "对照 PRD 独立验收"，G5）。
4. **去重**：新功能复用既有模块/接口时引用既有章节链接，不重复粘贴定义；`docs_code_divergence` 字段（§3.4）记录融合时发现的文档与代码分歧及采信结论。
5. **机读契约优先**：融合段落是 PRD/ADD JSON 的**人类可读沉淀**，Agent 间消费仍以 MinIO 上的 `prd.json` / `add.json` 为准（D7）；融合是"事后归档"，不阻塞流水线运行。

**greenfield（repo 为空，D8 特例）例外：**

- 无既有主设计文档可依赖 → PO/Architect 输出**完整独立设计文档** `docs/02_详细设计/<project>.md`，作为该项目的 v1 设计基线；
- 该独立文档内部仍遵循 PRD/ADD 字段结构与融合约定，便于后续功能在其上继续增量融合；
- 项目级文档与系统级主文档通过"项目索引"章节互链，不混入系统主干（避免单文档无限膨胀）。

**融合纪律的边界（防滥用）：**

- 禁止为同一功能的每次迭代新建独立文档；版本演进在既有章节内以 `> 更新 YYYY-MM-DD` 追加并保留历史；
- 禁止把 PRD/ADD JSON 的机读字段"翻译"成独立文档再让下游读取——那会引入双源漂移；
- 文档膨胀预警：当主设计文档单章超过约定规模（如 > 80 章节或 > N 千行），触发"系统主干 + 项目分册"拆分，拆分后仍遵循锚点互链。

#### 3.6.4 架构设计格式（arc42）与绘图工具约定

## 3.7 Engineering Charter（工程宪章 / 角色共享价值观）

> 决策 D16：**建立跨角色共享的 Engineering Charter 作为七角色的唯一价值观来源**。Charter 采用"两层来源"模型——Layer 0 方法论骨架（外部公认、按角色映射、提供广度）+ Layer 1 经验护栏（内部踩坑、精简、随问题增长）。原则以"引用式义务"书写（指名框架而非指定实现），既避免从零发明原则的主观性，又保留 agent 在框架内的自主判断空间。

> 决策 D17：**ADD schema 扩展 `design_patterns` 与 `dependencies_rationale` 两个字段**（见 §3.4 ADD schema），作为 Charter 在 Architect 产出上的强制落点；Reviewer 须核验二者齐备，缺失即驳回。

### 3.7.1 两层来源模型

Charter 不依赖个人经验堆砌，而是锚定到行业公认方法论（结构见下图示意）：

- **Layer 0 方法论骨架**：每个角色映射 2–4 个具名框架（§3.7.2），这些框架在 agent 训练语料中大量存在，"遵循 SOLID""按 arc42 第 9 章写 ADR"能直接激活具体先验，远比"写出可维护的好代码"有效。
- **Layer 1 经验护栏**：仅承载已实际踩过的坑（当前 seed 见 §3.7.3），作为硬约束；后续遇新问题再追加，保持精简。

### 3.7.2 Layer 0 方法论骨架（角色映射）

| 角色 | 公认方法论骨架（写进 Charter 的引用式义务） |
| --- | --- |
| **Architect** | arc42（方案架构模板，D15 已采纳，**日常义务**）· **TOGAF 10（企业架构，仅 greenfield / 跨系统决策时参考，非日常义务）** · GOF 23 设计模式 · ADR（架构决策记录，对应 `tech_stack.choices[].alternatives_rejected`）· Clean / Hexagonal 架构 · 12-Factor（云原生）· ATAM（质量属性权衡）· **前端设计规范（Ant Design / Material Design 3 设计令牌 + Refactoring UI 规则手册，前端相关任务，见 §3.12）** |
| **Developer** | SOLID · Clean Code（命名/函数/去重）· DRY / KISS / YAGNI · TDD · 12-Factor · 依赖卫生（语义化版本、优先成熟库）· OWASP 安全编码 · **Refactoring UI 前端规则（对齐/间距/层级/色数，前端相关任务，见 §3.12）** |
| **PO** | INVEST（用户故事六标准）· 用户故事格式 · MoSCoW 优先级 · Given-When-Then 验收标准 · Kano（价值评估）· 需求追踪矩阵 |
| **Tester** | 测试金字塔（Mike Cohn）· ISTQB 基础 · 边界值/等价类 · 测试左移 · **视觉回归（对照 PRD.visual_acceptance，前端相关任务，见 §3.12）** |
| **Reviewer** | Google 代码评审规范（小变更、给 rationale、善意）· 四眼原则 · 评审设计而非仅 diff · 静态分析门禁 · **视觉验收核验（对照 ui_spec + PRD.visual_acceptance，前端相关任务，见 §3.12）** |
| **Ops Analyst** | **ITIL 4（IT 服务管理：事件/问题/变更/知识管理，与现有 Ops 活动逐条对应）** · SRE（SLI/SLO/错误预算）· 无责复盘 · Runbook 纪律（D9/D10 已部分落地） |
| **Team Leader** | RACI · 康威定律觉察 · 角色无重叠无空洞（G1） |

> 分层说明：Architect 行中 **arc42 管「方案级架构」（单个 feature / 系统，日常义务），TOGAF 10 管「企业级架构」（跨系统 / greenfield 对齐，仅参考）**，二者分层互补而非重复；Ops Analyst 行中 **ITIL 4 管「服务管理流程」（事件/问题/变更/知识），SRE 管「可靠性工程度量」（SLI/SLO/错误预算）**，二者双腿并列覆盖运维全维度。上述方法论均属 Layer 0「引用式义务」——仅指名参考、不新增强制 schema 字段，故扩展几乎零约束成本（见 §3.7.5 执行挂钩）。

### 3.7.3 Layer 1 经验护栏（seed + 增长规则）

当前 seed（来自实际观察，作为硬约束）：

1. **该用前端框架处不得原生 HTML 堆砌**（难以维护/扩展）——落到 Developer / Architect；
2. **不辞辛苦自研已有成熟库可解决的能力**——"优先采用而非自研"；仅在 `dependencies_rationale.category = self-built` 且记录理由时允许；
3. **架构设计须显式考虑并命名设计模式**——落到 ADD `design_patterns`。
4. **前端必须消费设计令牌与组件库，禁止硬编码视觉值**（颜色/间距/字号直写）——落到 Developer（强制）与 Reviewer（核验）；对应 ADD `ui_spec` 字段（§3.12）。
5. **必须指定组件库 + 令牌来源，禁止"自创设计系统"**——落到 Architect（Gate2 打回）；前端 UI 一致性上限由成熟设计系统决定，agent 不发明视觉风格（§3.12）。

增长规则：仅当真实踩坑且方法论骨架未覆盖时，才新增一条护栏；护栏须可校验（有对应 schema 字段或 Reviewer 检查项），避免原则堆成大杂烩。

### 3.7.4 写法规则：引用式义务

原则不写虚话，写为"指名框架"的引用式义务，例如：

- **Architect**：ADD 须① 按 arc42 第 9 章记录 ADR（落入 `tech_stack.choices[].alternatives_rejected`）；② 显式命名 GOF 模式及解决的问题（落入 `design_patterns`）；③ 第三方依赖填 `dependencies_rationale` 并标注 `category`。
- **PO**：用户故事须满足 INVEST；验收标准用 Given-When-Then。
- **Developer**：遵循 SOLID 与 Clean Code；优先成熟库，不重复实现标准库。
- **Reviewer**：核验 ADD 含 `design_patterns` 与 `dependencies_rationale`，PRD 用户故事满足 INVEST；缺失即驳回（D17）。

### 3.7.5 执行挂钩

- **机读契约**：ADD 的 `design_patterns` / `dependencies_rationale` 由 `skills/architecture-design/add.schema.json` 强制校验（D7）；PRD 的 INVEST 由 `skills/prd-authoring/` 校验。
- **Reviewer 门禁**：缺 Charter 落点字段即驳回（D17）。
- **角色定义**：七角色 soul / SKILL.md 均引用 §3.7 为价值观单一来源，不各自硬编码。

## 3.8 共识闸门与阶段评审（Consensus Gate）

> 决策 D18：**将"PRD↔ADD 对齐"落为可执行的阶段门（stage-gate）控制流**——feature 流水线在「PRD→设计」「设计→开发」两处插入共识闸门；闸门的共识参与者为 **Reviewer**（独立质量门禁），Team Leader 仅作流程所有者与终裁，不参与闸门讨论本身；闸门按任务类型缩放，并复用 D6 回退协议。

### 3.8.1 设计动机

真实软件公司中，PO 的 PRD 与 Architect 的 ADD 并非各写各的，而需经「对齐—讨论—共识」后才推进；Architect 的 ADD 同样需与 Developer 确认可实施性。这一精神对应本项目的两个控制流构件：

- **Gate1（PRD 评审）**：`prd_drafting → prd_review → designing`。参与方 **PO + Architect + Reviewer**，核验 PRD 的需求完整性、验收标准可测试性、与 Charter（§3.7）一致性；Reviewer 持有 sign-off。
- **Gate2（设计评审）**：`designing → design_review → developing`。参与方 **Architect + Developer + Reviewer**，核验 ADD 的技术选型合理性、设计模式命名、`dependencies_rationale` 齐备、可实施性；Reviewer 持有 sign-off。

**Team Leader 不进入闸门讨论**：TL 是流程所有者（派单、超时重发、最终 `Verdict: SUCCESS/FAIL`），闸门讨论的共识由 Reviewer 作为独立质量门禁汇总与签署。Reviewer 对闸门的 sign-off 与对最终产物的终检（code review + 对照 PRD 验收）共同构成 TL 给出 `SUCCESS` Verdict 的前置条件——二者分离但互补，不合并（呼应 D1 双角色边界，避免双 leader 冲突）。

### 3.8.2 闸门协议（"开会"在 Agent 中的实现）

闸门不是真人会议，而是 Team Leader 编排的一段 **critique 循环**子协议：

1. **发起**：上游产物（PRD / ADD）就绪，TL 触发对应闸门，将产物分发参与方。
2. **critique 轮次**：各参与方返回 `sign-off` 或带理由的 `objection`（指出具体问题，而非泛泛"不好"）；
3. **讨论与收敛**：存在实质性异议时，进入限定轮次讨论（建议上限 **2 轮**，避免无限挑刺），生产者据反馈修订产物；
4. **终裁**：
   - 全体 `sign-off` → 闸门通过，进入下一阶段；
   - 达上限仍有异议 → **Team Leader 终裁**（投票或 TL 直接决定，复用 D6 回退仲裁风格），终裁结论写入产物留痕；
5. **驳回回路**：闸门驳回且判定为产物缺陷 → 回流至对应生产者（PO / Architect），复用 D6「`failure_class` 分类 → TL 仲裁回退」协议，不另造回退机制。

### 3.8.3 按任务类型缩放（避免闸门过载）

| 任务类型 | Gate1（PRD） | Gate2（设计） | 说明 |
| --- | --- | --- | --- |
| **feature** | 完整开启 | 完整开启 | 量少、价值高、易跑偏，值得双闸门 |
| **bug** | 不适用（无 PO/PRD） | 降级为 Architect 修复方案简审（可并入现有分析） | 避免为每个 bug 开双闸门放大 G3 已标注的串行延迟 |
| **incident** | 不适用 | 最轻（连 ADD 都可能无，Op 分诊即前置） | 走 Ops 分诊，闸门不应阻塞应急 |

> 缩放原则：**执行类环节（Dev→Tester）无需共识、验证类环节（Tester→Reviewer）独立把关**，二者均不加闸门——共识闸门只设在"需求↔设计""设计↔开发"两个易错配的接口处。

### 3.8.4 与现有机制的复用关系

- **复用 D6 回退协议**：闸门驳回、Tester 失败、Reviewer 终检驳回，回退目标均为对应生产者，分类由 `failure_class` 承载。
- **复用 §3.7 Reviewer 门禁**：Gate2 直接复用 D17 对 ADD `design_patterns` / `dependencies_rationale` 的核验；Gate1 复用 PRD 的 INVEST 校验（§3.7.5）。
- **不新增角色、不新增工件类型**：闸门是控制流构件，产物仍走既有 PRD / ADD JSON 契约（D7 / D12 / D13）。
- **可选增强（非强制）**：生产影响大的 feature，可在 Gate2 拉 Ops Analyst 进来看"可部署性"，但默认不强制。

## 3.9 Reviewer 资深化机制（决策 D19）

### 3.9.1 核心判断

在真人公司，资深 reviewer 靠四样：**选拔（能力强）、全局视野、脑子里的评审方法论、能拍板的权威**，外加多年积累。在 agent 世界，"资深"不是头衔，而是若干可工程化杠杆的叠加——且比现实更可控（可直接装配）。**决策 D19：Reviewer 必须在构造上成为七角色中的最强节点**，通过下列杠杆实现。

### 3.9.2 五杠杆模型（权重经 L2 修正后重排）

| 杠杆 | 对应现实 | 落地方式 | 权重 |
| --- | --- | --- | --- |
| **L1 模型档位最高** | 选拔（能力强） | Reviewer 用最高档模型，**高于 Architect / Developer**；角色表「模型建议」列标注（见 §3.9.6） | 主 |
| **L2 信息（修正后）** | 全局视野 | 见 §3.9.3——已降级为「事后互补信号 + 新鲜视角」，非文档权限 | 辅 |
| **L3 Charter 检查表** | 脑子里的评审方法论 | §3.7 Charter 外化为可照做清单，Reviewer 系统执行（INVEST / `design_patterns` / `dependencies_rationale` / OWASP / arc42 完整性） | 主 |
| **L4 否决权威** | 能拍板 | 可驳回、须附 `failure_class`、阻断 Verdict（D4 / G5），天然不妥协 | 不变 |
| **L5 经验闭环** | 多年职业积累 | lessons-learned（pgvector）回灌评审准则，每次缺陷沉淀为可复用判断 | 主 |

**选拔机制**（"经过选拔"这个动作本身）：以 SWE-bench Verified 或一批已知缺陷样本做基准，测候选模型 / 模板的抓缺陷能力，选最强者上岗——可量化、可复选，是字面意义的"招聘考试"。

### 3.9.3 L2 修正：Reviewer 没有文档访问优势

原直觉"Developer 只看到自己 diff"有误。Developer 实现 ADD 必读 ADD，且 PRD 作为「为什么做」的上下文也应给到 Developer（见 §3.9.4）——**PRD + ADD 是共享基线，Reviewer 在文档权限上无优势**。

Reviewer 真实的信息增量，来自 Developer 实现时结构上拿不到的东西：

- **完整 PR 级集成 diff**（看全貌，而非局部 working view）；
- **Tester 结果 / 覆盖率**（实现后才产生，Developer 实现时看不到自己的测试结论）；
- **KG 影响子图**（D4，系统级波及面，一般不要求 Developer 关注）；
- **lessons-learned 库**（历史缺陷模式）；
- **闸门 critique 记录**（他人已提过的异议）。

更关键的是**认知视角不对称**（不依赖信息量）：Developer 对自己写的实现有「近距盲区」，默认自己写的就是对的；Reviewer 零实现投入、全新推理，天然抓不同问题——这恰是真人资深评审的精髓，agent 版可直接复现。

### 3.9.4 Developer 输入集明确（设计点）

**Developer 输入集 = { PRD + ADD + Charter + 自己的任务范围 }。** PRD / ADD 作辅助上下文可降低误实现（从验收标准反推应做到什么程度），且现实公司本就如此。此设计**不威胁 Reviewer**——后者强项在整合全貌 + 事后信号 + 新鲜视角（§3.9.3），角色表 Developer 行已注明（见 §3.9.6）。

### 3.9.5 边界与取舍

- **硬上限**：模型本身的能力天花板；L1 永远选当下能拿到的最强模型，其余杠杆在该天花板上拉满「发挥率」。别指望靠 checklist 弥补模型根本差距。
- **成本 / 延迟**：最高档模型 + 最广上下文更贵更慢，但闸门漏检代价更高，值得；属 G3 已标注的串行延迟需克制，勿为资深化再堆双重评审。
- **不过度设计**：仅高危变更可上复审（reviewer-of-reviewer 或 TL 兜底），默认单 Reviewer 即可。

### 3.9.6 角色表落点

- **Reviewer**「模型建议」列：**GLM-5.2**（SiliconFlow 平台审查最强，见 §3.10），模型档位高于 Architect（kimi2.7code）/ Developer（DeepSeek-V4-Pro）。
- **Developer**「关键职责」列：feature 实现输入集含 PRD + ADD + Charter 作辅助上下文（§3.9.4）。

## 3.10 角色-模型映射（决策 D21）

### 3.10.1 选型三原则

- **异构防盲点**：设计（kimi）≠ 实现（DeepSeek）≠ 审查（GLM）三环全异构，盲区最大分散，闸门才真有效——尤其 Architect 与 Reviewer 必须不同模型家族，否则"自己写自己审"同源盲点会使闸门形同虚设。
- **各取所长**：审查用 GLM-5.2（白盒审查/漏洞发现国产第一梯队）；架构设计用 kimi2.7code（读代码库/写 ADD 强）；需求语义层用 Qwen（指令遵循强，且 PO 不写代码不需编程模型）。
- **成本分层**：高频调用角色（Developer / Tester / Team Leader / Ops Analyst）用 DeepSeek-V4-Pro 双档价（off-peak 半价）；低频高价值角色（Architect / Reviewer / PO）用专用模型。

### 3.10.2 实际映射（基于 SiliconFlow 平台可用清单）

> 决策 D21：角色-模型映射以**平台实际可服务模型**为准，下表为当前 SiliconFlow 可用上限；模型下线/升级时按 §3.10.5 路径替换，异构结构不变。

| 角色 | 模型（SiliconFlow 实际） | 匹配逻辑 |
| --- | --- | --- |
| **Team Leader** | DeepSeek-V4-Pro | 综合强、决策稳、双档定价；协调/仲裁不需极端编程，延续现主力 |
| **PO** | Qwen3.6-35B-A3B | Qwen 系指令遵循仍属国产前列 → PRD / 验收标准严循 Charter（INVEST / Given-When-Then）不跑偏；需求语义层不需顶级编程 |
| **Architect** | kimi2.7code | code 模型读代码库 / 做设计强；**与 Reviewer(GLM) 异构**；调用低频 |
| **Developer** | DeepSeek-V4-Pro | 编程实现 + 双档定价性价比最高（最高频）；与 Architect(kimi) 异构 |

### 3.10.3 异构校验

- 设计（kimi2.7code）≠ 实现（DeepSeek-V4-Pro）≠ 审查（GLM-5.2）三环全异构 → 盲区最大分散；
- PO（Qwen）独立语义层，与实现/审查家族分离；
- Team Leader / Developer / Tester / Ops 共用 DeepSeek（高频省钱，且不与"设计≠审查"异构主链路冲突）。

### 3.10.4 能力让步说明（诚实交代）

1. **Reviewer 从 GLM-5.3 降回 GLM-5.2**：CyberGym 低约 7pt（77.2 vs 84.5），但 GLM-5.2 仍是平台上能拿到的最强审查模型，且远强于 DeepSeek-V4（安全检测仅约 17% F1）。闸门有效性主要靠"异构 + Charter 检查表 + lessons 闭环"（§3.9），模型档位是加分项，5.2 够用。
2. **Architect 用 kimi2.7code**：code 专用版，综合推理略弱于 K3，但读 repo、写 ADD / arc42 足够；无多模态不影响架构设计。
3. **PO 用 Qwen3.6-35B-A3B**：比 Max 指令遵循弱一档，但 35B MoE 产出结构化 PRD / 验收标准足够。

### 3.10.5 升级路径（架构已留口）

当 SiliconFlow 上架更强模型时，直接替换对应角色，**异构结构不变，换模型不破坏设计**：

- Reviewer：GLM-5.2 → **GLM-5.3**（审查再跃升，CyberGym 全球第一梯队）；
- Architect：kimi2.7code → **Kimi K3**（综合设计 + 原生多模态）；
- PO：Qwen3.6 → **Qwen3.8-Max**（指令遵循更强）。

### 3.10.6 选拔机制落点（呼应 §3.9 选拔）

模型推荐是经验性结论，落地前应以 SWE-bench Verified + 一批已知缺陷样本做一轮基准，验证 Architect / Reviewer / Developer 的组合确实比"全 DeepSeek-V4-Pro"漏检更少、设计更合理——可量化、可复选，是字面意义的"招聘考试"。

## 3.11 需求澄清闸门（Gate0，决策 D22）

### 3.11.1 问题与行业锚定

> 决策 D22：feature 流水线在 PRD 起草前插入**需求澄清闸门（Gate0）**，由 PO 以 DoR 检查表卡住歧义需求，**禁止自造需求或默认假设**，经 User Channel 阻塞等待用户澄清，确认无歧义后才放行进 PRD 起草。

真人 PO 防"囫囵吞枣"靠两样公认方法：**DoR（Definition of Ready，就绪定义）**——需求须满足一组准入标准（清晰、无歧义、有可测试验收标准、优先级明确）才能进开发；以及**用户故事三 C 之 Conversation**——Card（写下来的故事）、**Conversation（与用户对话澄清）**、Confirmation（验收标准）。Conversation 即"来回确认"环节，是方法论明文要求，非临时补丁。本闸门 = 把 DoR 变成 PO 的**强制前置**。

### 3.11.2 澄清循环（Clarification Loop）

1. PO 收到需求 → 跑 DoR 检查表（对应 §3.7 PO 原则 + INVEST / 可测试验收）；
2. 通过 → 起草 PRD，进 §3.8 Gate1（PRD 评审）；
3. 不通过 → PO 生成**结构化澄清问题清单**（歧义点 + 为何阻塞 + 建议选项）→ 经 User Channel 发出 → **阻塞等待**；
4. 用户回复 → PO 重评 DoR → 回到 2 / 3；
5. 最大轮次（建议 **3**）仍不清 → 交 Team Leader 仲裁或挂起（复用 §3.9 阻塞 / 等待机制）。

### 3.11.3 User Channel 抽象（与通道解耦）

| 渠道 | 落地方式 | 备注 |
| --- | --- | --- |
| Jira issue | 回 comment 承载问题清单；**并将 issue 状态置为 `Needs Clarification`**，使下游自动化天然阻塞、澄清可追溯 | comment 为问题载体，状态位为阻塞开关 |
| 聊天室 | 直接对话式澄清，PO 用对话上下文累积理解 | 实时往返 |
| 抽象层 | PO 只调 `ask_user(questions)`，底层路由到 Jira / 聊天室 / 其他；回复经同一接口回流 | PO 逻辑与通道解耦 |
| 产物留存 | 澄清过程落 `clarification.json`（MinIO，与 PRD / ADD 同机制），含问题 + 用户回复 + 轮次，供 Reviewer / TL 审计"需求是否真澄清过" | 可追溯、可核验 |

### 3.11.4 防"瞎编"硬约束

- **DoR 强制**：`user_stories` / `acceptance_criteria` 字段不得填"待定"或 PO 自造；未澄清前不得进 PRD 起草。
- **澄清是"问"非"替定"**：PO 列选项供用户选，不自己拍板需求实质；判断权始终在用户。
- **轮次上限防无限循环**：超限交 TL 仲裁 / 挂起，不无限挑刺（复用 §3.9 阻塞机制）。

### 3.11.5 与现有设计衔接

- 这是 **Gate0**，位于 §3.8 Gate1（PRD 评审）**之前**；Developer 最终拿到的 PRD 已是澄清后的（呼应 §3.9.4"给 Dev PRD + ADD 作辅助"——辅助有效的前提是 PRD 本身清楚）。
- 复用 §3.9 的"阻塞 / 等待"与 TL 仲裁，不新造机制。
- **范围**：仅 feature / greenfield 走此闸门；bug（走复现步骤）/ incident（走告警）通常已有明确描述，不需澄清。

## 3.12 前端视觉能力与设计规则（决策 D23）

> 决策 D23：**LLM 前端视觉短板以工程化方案解决，而非提示词优化**——核心判断：视觉质量短板本质不是"生成能力"不足，而是**感知反馈回路缺失**（真人前端靠"渲染 → 看效果 → 调整"迭代，agent 在纯文本通道盲写 CSS/JSX 且从不"看见"渲染结果）。解法分两条通道：**通道 A 文字化**（Playwright 提取 DOM 结构化数据 → 规则引擎判定，主力、零模型成本）与**通道 B 原生多模态**（截图注入 VLM 语义判断，本阶段暂缓、预留接口）；同时把"基本的审美"工程化为可判定的设计规则体系（原则层 / 护栏层 / 数据层 / 阈值层），按角色分配。

### 3.12.1 核心判断与设计原则

1. **截图 ≠ 看懂**：Playwright 只是传感器；"看见"靠两条通道，主力通道不需要图像理解；
2. **审美 = 规则而非品味**：不教模型"有品味"，而是把"基本审美"翻译成可判定的规则（90% 的"丑"是可判定缺陷：没对齐/间距乱/颜色多/层级糊）；
3. **不新增角色、不动状态机**：全部落点为工具 + schema 字段 + Charter 条款 + soul 段落，与既有机制（G5 工件契约、D7 MinIO 传递、D6 回退协议）完全复用。

### 3.12.2 visual_check 工具（工具层，单一统一工具）

**工具能力**（挂工具层，非角色私有，四角色共享）：

| 能力 | 实现 | 说明 |
| --- | --- | --- |
| dev server 生命周期 | 检测端口存活 / 拉起 / 退出 | Developer 本地自检与 Tester 回归共用 |
| 通道 A：DOM 结构化提取 | Playwright `page.evaluate()` 执行 `getBoundingClientRect` / `getComputedStyle` / canvas 色值采样 → 结构化 JSON | **主力**：对齐/间距/字号/色数/对比度全部纯计算可判，零模型成本；文本模型（含无多模态的 GLM-5.2）通过该通道"看见"页面 |
| 通道 B：原生多模态（预留） | `page.screenshot()` → PNG base64 → VLM 注入 | 仅语义判断（风格一致性）；**本阶段暂缓**（成本高、VLM 细粒度审美分辨率有限），接口预留 `screenshot_path` 字段，等 §3.10.5 升级路径中 Kimi K3（原生多模态）到位后无侵入接入。**"暂缓"的精确含义**：截图可落盘留档供人审计，但**不注入 VLM、不参与自动判定**——即本阶段所有判定均基于通道 A 的结构化数据 |
| 规则引擎 | 按 §3.12.4 阈值纯代码判定，输出结构化报告 | 判定不依赖模型，可复现 |

**角色调用协议差异**（写进各角色 soul / prompt）：

| 角色 | 何时看 | 看什么 | 怎么用结果 |
| --- | --- | --- | --- |
| Architect | 设计阶段（仅前端任务） | 存量页面 DOM/组件结构快照 | 提取视觉基线写入 `ui_spec.baseline_sources`，ui_spec 才有锚点 |
| Developer | 每次前端改动后、提交前 | 结构化快照对照 `ui_spec` | 自检循环 ≤3 轮；**内部消化不进状态机**，避免污染 failure_class（超限处理见下方执行约定 3） |
| Tester | 回归测试阶段 | 本次结构化快照 + 基线快照 + 对照 `PRD.visual_acceptance` | 视觉回归证据入 TestReport；差异 → `failure_class=visual` |
| Reviewer | 审查阶段 | 结构化快照 + 对照 `PRD.visual_acceptance` 与 `ui_spec` | 逐项 yes/no 核验；不通过 → `revise` 回退 |

**执行约定（消除歧义，写进 visual-check 技能与各角色 soul）：**

1. **前端相关任务判定**（决定 ui_spec / visual_acceptance 是否必填、是否触发 visual_check）：满足任一即算——① `ADD.change_plan` 涉及前端文件扩展名（`.tsx` / `.jsx` / `.vue` / `.svelte` / `.css` / `.scss` / `.less` / `.html`）；② PRD 含 `visual_acceptance` 字段。纯后端任务不触发，零额外开销。
2. **视觉基线来源**（解决"首次无基线"问题）：
   - feature（存量项目）：优先用 Architect 提取的 `ui_spec.baseline_sources`；无存量页面时，由 Tester **首次运行生成基线快照**，落 MinIO 与 `prd.json` 同级目录，后续回归与基线比对；
   - greenfield：无存量可提取，由 Tester 首次运行生成基线快照；`ui_spec.design_tokens` 直接引用前端脚手架预装的设计系统（见 §3.2 greenfield 特殊化）。
3. **Developer 自检超限（>3 轮仍未全过）处理**：**停止自检、正常提交**，但须在提交物中附 `visual_check` 报告并显式标注未通过项。自检是"尽力而为的提前拦截"，**不是放行条件**——最终由 Tester / Reviewer 判定，违规则按 `failure_class=visual` 回退 Developer。此设计避免自检循环拖长串行延迟（呼应 §7 延迟风险）。
4. **bug 场景范围**：本阶段 `visual_check` **仅用于 feature / greenfield**。前端视觉类 bug 沿用 bug 流程（Developer 最小修复），不强制视觉回归、不填 `ui_spec`，避免给高频 bug 流增加成本。

### 3.12.3 前端设计规则体系（参照物与来源）

不写虚的审美描述，引用已有成熟规则体系，按四层落点：

| 层 | 内容 | 参照物（成熟来源） |
| --- | --- | --- |
| **原则层**（Charter Layer 0，全员共享） | 格式塔四原则（邻近/相似/连续/闭合）、层级（视觉权重=信息重要性）、一致性、克制（少即是多） | 《Refactoring UI》（Adam Wathan & Steve Schoger）——写给工程师的设计书，规则全部"别做 X，做 Y"式可操作化，最适合作 LLM 参照物 |
| **硬标准层**（可强制执行） | WCAG 2.1 AA（正文对比度 ≥4.5:1 / 大字 ≥3:1）、点击目标 ≥44×44px、8pt 网格 | WCAG 2.1、Apple HIG、Material 8pt 网格 |
| **令牌库层**（ui_spec 数据） | 色板/字号阶梯/间距/圆角/阴影等设计令牌，直接抄成熟系统 | Ant Design 设计规范（首选，与 React+AntD 选型对齐，令牌即组件实现）、Material Design 3 tokens |
| **阈值层**（visual_check 规则引擎） | 可执行阈值（见 §3.12.4），纯代码判定 | 由上述来源蒸馏 |

### 3.12.4 可执行阈值清单（visual_check 规则引擎）

| 规则 | 阈值 | 判定方式 | 来源 |
| --- | --- | --- | --- |
| 对比度 | 正文 ≥4.5:1 / 大字 ≥3:1 | 色值计算 | WCAG 2.1 AA |
| 间距节奏 | ∈ {4,8,16,24,32,48} 且组间距 > 组内间距 | DOM 计算 | 8pt 网格 / MD3 |
| 字号层级 | 全页字号 ≤3–4 种；阶梯比 1.2–1.25；正文行高 1.4–1.6 | DOM 计算 | Refactoring UI |
| 色数 | 主色 ≤1 + 中性色 + 语义色（60-30-10） | 色值采样 | Refactoring UI |
| 对齐 | 同组元素共用一条对齐轴，不混轴 | DOM 计算 | Refactoring UI |
| 层级 | 每屏 primary button ≤1 | DOM 计算 | AntD / MD3 |
| 圆角/阴影 | 圆角 ≤2–3 种取值；阴影 ≤2 档 | DOM 计算 | 设计令牌 |
| 溢出 | ① 每个文本容器须声明溢出策略（ellipsis/wrap）；② 实测内容不越界（`scrollWidth ≤ clientWidth` / `scrollHeight ≤ clientHeight`） | DOM 计算（通道 A） | 工程惯例 |
| 一致性 | 同类组件样式一致；与基线风格一致 | VLM 语义判断（通道 B，**暂缓**） | ui_spec 基线 |

> **通道归属**：上表前 8 项（对比度 / 间距节奏 / 字号层级 / 色数 / 对齐 / 层级 / 圆角阴影 / 溢出）均由通道 A 纯计算判定，**零模型成本、可复现**；仅末项「一致性」依赖通道 B，本阶段暂缓。
>
> **边界声明**：本阶段视觉护栏以**可计算规则为上限**，语义一致性靠 Developer 自检对照 `ui_spec` + Reviewer 抽查兜底，不做自动判定。

### 3.12.5 角色-设定分配矩阵（给谁什么设定）

| 角色 | 获得设定 | 触发时机 | 判定/产出 |
| --- | --- | --- | --- |
| PO | Gate0 DoR 检查表增「视觉预期是否明确（页面结构/空态/错误态呈现）」；PRD 模板补 `visual_acceptance` 字段 | 需求澄清（feature/greenfield） | PRD 含视觉 Given-When-Then |
| Architect | `ui_spec` 产出义务（引用成熟设计系统，禁止自创）；Playwright 提取存量页面视觉基线 | 设计阶段（前端任务） | 产出 `ui_spec`，Gate2 自检通过 |

| Team Leader | 无需新增设定（failure_class=visual 复用既有仲裁路径） | 回退仲裁 | 按 D6 改判/回退 |

### 3.12.6 模型决策（D23 附带结论）

- **主模型不动**：Developer（DeepSeek-V4-Pro）/ Tester（DeepSeek-V4-Pro）/ Reviewer（GLM-5.2）保持 §3.10 映射，异构结构（D21）不受影响；通道 A 让无多模态模型也能"看见"；
- **多模态暂缓**：通道 B 本阶段不落地（VLM 抓粗大缺陷可靠、细粒度审美判断分辨率有限，且成本高），仅预留接口；等 §3.10.5 升级路径（Kimi K3 原生多模态）到位后再议；
- **视觉判断分布式产生、Verdict 单点作出**：视觉结论可由 Tester/Reviewer 各自产生，但最终 Verdict 仍归 Team Leader（对齐 L4 否决权威）。

## 附录 A：运维团队接入设计（incident 场景）

### A.1 背景与定位

当前推进方向是"整个软件公司"，但实际覆盖的主要是开发团队；运维（生产环境侧）未接入。运维与开发的本质分工：

| 维度   | 开发团队                    | 运维（Ops Analyst）                              |
| ---- | ----------------------- | -------------------------------------------- |
| 关注对象 | **静态**代码（repo 即真相源）     | **动态**生产环境（运行态、流量、配置、基础设施）                   |
| 问题形态 | bug / feature / 从 0 到 1 | incident：出了问题，**不确定是否代码问题**                  |
| 知识源  | 源码 + docs + 代码索引（KG/向量） | 部署文档 + runbook + 历史事件库 + **实时环境信号**（日志/服务状态） |
| 异质性  | 低（代码处理高度标准化）            | 高（不同公司/产品部署环境差异大，且部署脚本与实际配置通常**不入代码库**）      |

该设计对齐业界实践：ITIL 事件管理（Incident，恢复服务优先）与问题管理（Problem，根因修复）的分离，即 SRE 的标准分工。

### A.2 incident 流程与 L0/L1/L2 操作分级

**流程**（主状态机 incident 分支的展开）：

```
incident 进入
  └─ Ops Analyst 分诊（ops_diagnosing）
       ├─ 读环境资产包（env.yaml 拓扑 + runbook 索引 + 部署文档）
       ├─ lesson-lookup 检索历史事件（pgvector）
       ├─ L0 只读检查：服务状态 / 端口 / 进程 / 磁盘 / 网络 / 配置漂移比对
       └─ 产出诊断报告（classification: env | code | data | unknown）
            ├─ env 问题 → ops_remediation：处置建议（标注 L1/L2 + 步骤 + 回滚点）→ 人执行 → 确认后 resolved
            ├─ code 问题 → 归一化为 bug 任务（诊断报告作为证据包随行）→ analyzing
            └─ unknown → escalated 转人工
```

**生产操作三级纪律**（D9，写入 ops-analyst soul 的硬性规则）：

| 级别            | 类型  | 示例                                    | Agent 权限                      |
| ------------- | --- | ------------------------------------- | ----------------------------- |
| **L0 只读**     | 查看类 | 读日志、查指标、health check、`docker ps`、配置比对 | 自动执行，无需审批                     |
| **L1 可逆低危**   | 恢复类 | 重启单实例、清缓存、刷新连接                        | **只出建议 + 操作步骤**，人确认后代执行或人手动执行 |
| **L2 不可逆/高危** | 变更类 | 扩缩容、数据订正、改生产配置、切流量                    | **只出分析报告与方案，人执行**，Agent 无执行接口 |

第一阶段结论：L0 全放开 + L1/L2 全部人执行（即"只做分析报告，最后由人操作"）。理由：诊断是 LLM 价值最高、风险最低的环节；执行依赖的审批工单 + 操作审计 + 回滚点三件套是独立基础设施课题，不阻塞本次接入。L1/L2 处置建议经 `escalated` 通道送达 admin-human，天然复用现有人工协作机制。

**双向分流，而非单向守门**：

- 正向：诊断报告（含已排除的环境变量清单）随归一化后的 bug 任务传递，Architect 根因分析直接继承排查结论，显著缩小代码搜索范围；
- 反向：bug 流程中复现脚本无法复现 → `failure_class=environment` 回退 Ops Analyst 复查（避免间歇性环境问题导致 Developer 空转三轮烧尽重试预算）。

### A.3 诊断报告 schema（Ops Analyst 产出）

```json
{
  "task_id": "INC-XXXX",
  "env": "prod",
  "symptom": "症状一句话复述",
  "env_checks": [
    {"item": "service:api 状态", "result": "running|degraded|down", "evidence": "docker ps 输出摘要"},
    {"item": "disk_usage", "result": "92% (阈值 90%)", "evidence": "df -h 输出"},
    {"item": "config_drift", "result": "无漂移|列出漂移项", "evidence": "与资产包基线配置 diff"}
  ],
  "lessons_hit": [{"lesson_id": "...", "similarity": 0.87, "applied": true}],
  "classification": "env | code | data | unknown",
  "suspected_cause": "疑似原因与推理链",
  "recommended_action": {
    "level": "L0 | L1 | L2",
    "steps": ["具体操作步骤（可执行级描述）"],
    "rollback_point": "回滚点/恢复手段",
    "references": ["命中的 runbook 条目 / 部署文档章节"]
  },
  "excluded_for_dev": ["已排除的环境变量清单（供 Architect 继承）"],
  "sensitive_data_redacted": true
}
```

### A.4 环境资产包机制（D10，解决"部署脚本与实际配置不入代码库"）

部署产物不进代码库是常态（含真实配置值更敏感），因此运维的知识源不能照搬"clone repo"模式，改为**随环境交付的资产包约定**，存放于平台已有的 MinIO 共享存储：

```
envs/{env}/                     # 如 envs/prod/
  ├── env.yaml                  # 拓扑清单：服务列表、依赖关系、部署形态、日志位置、监控面板入口、健康检查端点
  ├── runbooks/                 # 已知故障模式的诊断路径 + 处置动作 + 风险等级标注（L0/L1/L2）
  ├── deploy/                   # 实际部署脚本与生效配置（脱敏版：凭据替换为占位符）
  └── baseline/                 # 配置基线快照（供配置漂移比对）
```

要点：

- **复用现有接入机制**：worker 已通过平台注入的 `mc` CLI（agentteams alias）访问 MinIO，Ops Analyst 拉取资产包与现有"拉仓库代码"同一模式（`mc cp envs/prod/... → 本地`）；
- **权限隔离**：`envs/` 路径仅 ops-analyst 角色可读（MinIO 路径级策略），开发角色不可见真实配置；
- **脱敏纪律**：资产包内配置为脱敏版（凭据占位符）；诊断报告与房间消息**严禁出现明文凭据**（soul 硬性规则 + 报告发布前 redaction 检查，schema 中 `sensitive_data_redacted` 字段自证）；
- **异质性吸收**：Agent 能力（诊断流程骨架）标准化，环境差异全部进入资产包数据——与 Architect「docs 优先，无 docs 则源码逆向」对称：**runbook 优先，无 runbook 则按通用诊断 playbook 降级，事后沉淀新 runbook 条目**。

### A.5 运维技能盘点：现有技能复用与缺口

**现有 15 个技能的适配性分析：**

| 技能                                                                                                                                                             | 复用判定                       | 运维用途                                                          |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------- | ------------------------------------------------------------- |
| `bash-exec`                                                                                                                                                    | ✅ 直接复用                     | 核心执行器：health check、日志查看（tail/grep）、`docker ps`、连通性测试等全部 L0 检查 |
| `code-read`                                                                                                                                                    | ✅ 直接复用                     | 读部署文档、runbook、env.yaml、配置文件（通用文件阅读，不限于源码）                     |
| `lesson-lookup`                                                                                                                                                | ✅ 直接复用                     | 历史事件/Postmortem 检索（pgvector 已有，运维是天然消费方）                      |
| `knowledge-extraction`                                                                                                                                         | ✅ 直接复用（角色字段增补 Ops Analyst） | incident 复盘沉淀：新 runbook 条目 + lesson 入库                        |
| `result-judge`                                                                                                                                                 | ⚠️ 可选复用                    | 诊断结论的裁定格式（非必需，诊断报告 schema 已覆盖）                                |
| `root-cause-analysis`                                                                                                                                          | ⚠️ 方法论复用                   | 证据链推理方法可借鉴，但其工具面（Neo4j 代码调用链）面向代码，不直接适用                       |
| `code-search` / `module-lookup` / `impact-analysis` / `repo-index` / `repair-planning` / `patch-generate` / `multi-file-edit` / `test-run` / `pipeline-router` | ❌ 不适用                      | 代码侧专属                                                         |

**结论：4 个直接复用，需新增 2 个：**

| 新技能                  | 内容                                                                        | 解决的问题                                     |
| -------------------- | ------------------------------------------------------------------------- | ----------------------------------------- |
| `ops-diagnosis`（B9）  | incident 诊断 playbook：L0 检查清单、证据链规范、失败树排查路径、诊断报告 schema、L0/L1/L2 操作纪律、脱敏规则 | 运维侧缺"诊断方法论"载体（对应开发侧的 root-cause-analysis） |
| `env-inventory`（B10） | 环境资产包读取约定：MinIO `envs/{env}/` 路径规范、env.yaml 格式、runbook 索引、脱敏访问规则          | 部署脚本与实际配置不入代码库 → 环境知识可达性（用户指出的关键缺口）       |

**不新增 MCP 原语**：第一阶段 L0 检查全部经 bash-exec 完成（worker 容器内执行只读命令），资产包经 mc CLI 拉取；日志/监控的专用只读 MCP 工具（Prometheus 查询、日志检索 API）列为后续演进项。

**Ops Analyst 技能配置汇总**：`ops-diagnosis` + `env-inventory` + `bash-exec` + `code-read` + `lesson-lookup` + `knowledge-extraction`（六项；刻意不给代码检索类技能，与 PO「不给代码技能」同理——职责边界即技能边界）。

### A.6 参数适配（incident 场景的差异化配置）

| 参数          | bug/feature 场景 | incident 场景 | 理由                                                    |
| ----------- | -------------- | ----------- | ----------------------------------------------------- |
| 任务超时        | 30min（沿用）      | 15min（诊断阶段） | MTTR 导向，分诊拖延直接放大故障时长                                  |
| 单阶段重试       | ≤ 2            | ≤ 1         | 环境类问题重试价值低，快速升级人工                                     |
| 全局轮次        | MAX_ROUND=3    | ≤ 2         | 同上                                                    |
| canary/发布等待 | 24h            | 不适用（无发布环节）  | incident 终态为 resolved（处置确认）或转 bug，不进 awaiting_release |

### A.7 演进路径（不进本次范围）

1. **审批代执行**（触发 Ops Responder 拆分）：审批工单 + 操作审计 + 回滚点三件套落地后，L1 级可由 Agent 在人批准后代执行；
2. **观测集成**：Prometheus/Grafana/日志平台只读 MCP 工具，替代 bash 直查，提升诊断覆盖面；
3. **告警驱动**：监控告警 → 自动生成 incident 任务信封（复用 Jira listener 路线图），形成"告警 → 分诊 → 处置/转开发"全自动入口；
4. **变更管理关联**：incident 诊断关联近期变更记录（谁改了什么），提升配置漂移类问题的定位速度。
